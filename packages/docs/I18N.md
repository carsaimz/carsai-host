# CARSAI HOST — Internationalization (i18n) Guide

CARSAI HOST ships with full internationalization support across four
locales: Portuguese (default), English, French, and Spanish. The i18n
system is designed so that the same translation files can be consumed by
the React frontend (via `i18next`), the Express backend (via a tiny
shared `translate()` helper), and the Capacitor mobile app (which reuses
the frontend bundle). This document describes how the system is
architected, how to add a new language, and how translators can
contribute.

---

## 1. Supported Locales

| Code | Language | Native name | Default? | File |
|------|----------|-------------|----------|------|
| `pt` | Portuguese | Português | Yes | `packages/shared/src/i18n/pt.json` |
| `en` | English | English | No | `packages/shared/src/i18n/en.json` |
| `fr` | French | Français | No | `packages/shared/src/i18n/fr.json` |
| `es` | Spanish | Español | No | `packages/shared/src/i18n/es.json` |

Portuguese is the default because the project was originally created for
the Portuguese-speaking community. All four locales are bundled with the
application and loaded eagerly — no network round-trip is needed to
switch languages. This trades a slightly larger initial bundle (each
locale is roughly 12 KB gzipped) for instant language switching and
offline support in the mobile app.

The list of supported locales is exported from
`packages/shared/src/constants/index.ts` as `SUPPORTED_LOCALES` (a
const tuple `['pt', 'en', 'fr', 'es']`) and from
`packages/shared/src/i18n/index.ts` as the same constant. The default
locale is `DEFAULT_LOCALE = 'pt'`. These constants are used both by the
frontend (to populate the language selector) and by the backend (to
validate the `locale` field on user registration).

## 2. Architecture

### 2.1 Shared JSON Files

All translations live as plain JSON files in
`packages/shared/src/i18n/`. Each file is a nested object where keys
are dot-notation segments and values are translation strings. The
structure is identical across all locales — a missing key in one locale
falls back to the default locale (`pt`), and if the key is missing there
too, the literal key string is returned (which makes missing
translations immediately visible during development).

The `pt.json` file is the canonical source of truth. Every key that
appears in any locale must also appear in `pt.json`. The CI pipeline
enforces this by running a script that diffs the key sets and fails the
build if any locale has a key that `pt.json` does not, or if `pt.json`
has a key that any other locale is missing.

### 2.2 Backend Loader

The shared i18n module at `packages/shared/src/i18n/index.ts` imports
all four JSON files using Node's native JSON module imports:

```typescript
import pt from './pt.json' with { type: 'json' };
import en from './en.json' with { type: 'json' };
import fr from './fr.json' with { type: 'json' };
import es from './es.json' with { type: 'json' };

export const translations = { pt, en, fr, es } as const;
```

It exports two functions:

- `getTranslation(locale: string)` — returns the JSON object for the
  given locale, falling back to `pt` if the locale is unknown.
- `translate(locale, key, vars?)` — resolves a dot-notation key (e.g.
  `"auth.login.title"`) into a string, applying `{{var}}`
  interpolation if `vars` is provided.

The backend uses `translate()` for transactional emails, audit log
messages, and any user-facing string that needs to be locale-aware. The
caller passes the user's `locale` field (stored on the `users` row)
which is set at registration based on the `Accept-Language` header or
explicit user choice.

### 2.3 Frontend Loader

The frontend uses `i18next` with the `react-i18next` bindings. The i18n
configuration lives at `packages/web/src/i18n/config.ts` and imports
the same JSON files from the shared package via the workspace symlink:

```typescript
import { translations, DEFAULT_LOCALE, SUPPORTED_LOCALES }
  from '@carsai/shared';

i18n
  .use(initReactI18next)
  .init({
    resources: {
      pt: { translation: translations.pt },
      en: { translation: translations.en },
      fr: { translation: translations.fr },
      es: { translation: translations.es },
    },
    lng: detectLocale(),
    fallbackLng: DEFAULT_LOCALE,
    supportedLngs: SUPPORTED_LOCALES,
    interpolation: { escapeValue: false }, // React already escapes
  });
```

Components consume translations via the `useTranslation` hook:

```tsx
import { useTranslation } from 'react-i18next';

function LoginPage() {
  const { t } = useTranslation();
  return <h1>{t('auth.login.title')}</h1>;
}
```

## 3. Locale Detection Order

The frontend determines the active locale at boot using a four-step
cascade. The first non-empty value wins; if all four are empty, the
default locale (`pt`) is used.

1. **localStorage** — `localStorage.getItem('locale')`. This is set
   whenever the user picks a language from the selector and persists
   across sessions on the same browser.
2. **Cookie** — `document.cookie` parsed for a `locale=...` entry. The
   cookie is set by the backend on the `/api/v1/auth/login` response so
   that server-rendered error pages (e.g. 404 from Nginx) can read it
   and serve a localised page.
3. **Accept-Language header** — parsed from `navigator.language` and
   `navigator.languages`. The first entry that matches a supported
   locale is used; "pt-BR" matches "pt", "en-US" matches "en".
4. **Default** — `pt`.

The detection logic lives in `packages/web/src/i18n/detect.ts`. The
selected locale is also stored on the `users.locale` column when the
user registers or updates their profile, so the backend can send
localised emails without re-detecting.

## 4. Adding a New Language

Adding a new locale is a five-step process. As an example, this is how
you would add German (`de`).

### 4.1 Copy the Reference File

```bash
cd packages/shared/src/i18n
cp pt.json de.json
```

Always copy from `pt.json` (the canonical source) rather than `en.json`
because `pt.json` is the locale that CI checks against. If you copy
from `en.json` and `en.json` happens to be missing a key that
`pt.json` has, your new locale will fail the CI key-parity check.

### 4.2 Translate Every Value

Open `de.json` in your editor and translate every string value to
German. Leave the keys unchanged. Preserve the `{{var}}` placeholders
exactly as they appear — the interpolation engine matches on `{{name}}`
literally, so `{{name}}` must remain `{{name}}` (not `[[name]]` or
`%name%`).

### 4.3 Register the Locale

Edit `packages/shared/src/i18n/index.ts` and add the import + entry:

```typescript
import de from './de.json' with { type: 'json' };

export const translations = { pt, en, fr, es, de } as const;
```

Then edit `packages/shared/src/constants/index.ts`:

```typescript
export const SUPPORTED_LOCALES = ['pt', 'en', 'fr', 'es', 'de'] as const;

export const LOCALE_LABELS: Record<string, { label: string; flag: string }> = {
  pt: { label: 'Português', flag: '🇵🇹' },
  en: { label: 'English',   flag: '🇬🇧' },
  fr: { label: 'Français',  flag: '🇫🇷' },
  es: { label: 'Español',   flag: '🇪🇸' },
  de: { label: 'Deutsch',   flag: '🇩🇪' },
};
```

### 4.4 Update the Zod Schemas

The shared Zod schemas in `packages/shared/src/schemas/index.ts`
include locale enums that must be extended:

```typescript
locale: z.enum(['pt', 'en', 'fr', 'es', 'de']).default('pt'),
```

There are two such schemas: `registerSchema` and `updateProfileSchema`.
Both must be updated so that the API accepts the new locale on
registration and profile update.

### 4.5 Add the Language to the Selector

Edit `packages/web/src/components/LanguageSelector.tsx` and add the new
locale to the dropdown options. The selector iterates over
`LOCALE_LABELS` so this happens automatically if you registered the
locale in step 4.3 — no code change is needed in the component, only a
rebuild.

After all five steps, run `pnpm build` and verify that the new language
appears in the selector and that switching to it shows the translated
strings. Run `pnpm test` to ensure the key-parity test passes.

## 5. Translation Key Conventions

### 5.1 Dot Notation

Keys are written in dot notation that mirrors the JSON nesting. For
example, the key `auth.login.invalidCredentials` corresponds to the
JSON path `auth.login.invalidCredentials` in the translation file.
This convention makes it easy to find the source of any string by
grepping for the key.

### 5.2 Namespaces

The top-level keys in the JSON files act as namespaces. The current
namespaces are:

| Namespace | Purpose |
|-----------|---------|
| `common` | Buttons, labels, and verbs used across the whole app |
| `nav` | Navigation menu items (header + sidebar) |
| `home` | Landing page hero, features, CTA |
| `auth` | Login, register, forgot/reset password, 2FA, OAuth |
| `dashboard` | Dashboard overview, stats, quick actions |
| `accounts` | Hosting account list, create form, details |
| `files` | File manager |
| `databases` | Database manager |
| `domains` | Domain list, DNS records, SSL |
| `ssl` | SSL certificate management |
| `backups` | Backup management |
| `cron` | Cron job management |
| `tickets` | Support tickets |
| `blog` | Blog posts and categories |
| `forum` | Forum categories, topics, replies |
| `profile` | User profile, security, API tokens |
| `admin` | Admin panel |
| `errors` | Error pages (404, 500, 403, 401) and error messages |
| `validation` | Form validation messages |
| `success` | Success toast messages |
| `footer` | Footer links and legal |
| `language` | Language selector labels |

When adding a new feature, create a new namespace rather than
overloading an existing one. This keeps the JSON files scannable and
makes it obvious which translation strings belong to which feature.

### 5.3 Naming Within a Namespace

Within a namespace, use camelCase for keys that map to UI labels
(`submit`, `forgotPassword`) and nested objects for groups of related
strings (`status.active`, `status.suspended`, etc.). Status enums are
always grouped under a `status` key so the frontend can render them
with a single `t(\`accounts.status.${status}\`)` call.

## 6. Interpolation

Variable interpolation uses the `{{varName}}` syntax. The `translate()`
function on the backend and i18next on the frontend both support this
syntax out of the box. Example:

```json
{
  "dashboard": {
    "welcome": "Olá, {{name}}"
  },
  "blog": {
    "publishedOn": "Publicado em {{date}}",
    "by": "por {{author}}"
  }
}
```

Backend usage:

```typescript
import { translate } from '@carsai/shared';

const body = translate(user.locale, 'dashboard.welcome', { name: user.firstName });
```

Frontend usage:

```tsx
const { t } = useTranslation();
return <h1>{t('dashboard.welcome', { name: user.firstName })}</h1>;
```

For pluralisation, i18next supports the `_one` / `_other` suffix
convention. The current translation files do not use plurals because
the app's strings are mostly labels and verbs, but the configuration
is in place if you need it. Use `t('blog.views', { count: 5 })` and
define `blog.views_one` and `blog.views_other` in the JSON file.

## 7. RTL (Right-to-Left) Support Considerations

Arabic, Hebrew, and Farsi are right-to-left languages that CARSAI HOST
does not currently ship translations for. If you add an RTL locale, the
following changes are required:

1. **HTML `dir` attribute**: the root `<html>` element must have
   `dir="rtl"`. The frontend should set this based on the active
   locale: `document.documentElement.dir = ['ar', 'he', 'fa'].includes(lng) ? 'rtl' : 'ltr'`.
2. **Tailwind RTL plugin**: install `tailwindcss-rtl` or use
   Tailwind's logical properties (`ms-4` instead of `ml-4`). The
   current codebase uses physical properties (`ml-4`, `pr-2`); a
   migration to logical properties is required for proper RTL support.
3. **Icon mirroring**: directional icons (chevrons, arrows) must be
   flipped. Use the `rtl:rotate-180` Tailwind variant on every
   directional icon.
4. **Date and number formatting**: use `Intl.DateTimeFormat` and
   `Intl.NumberFormat` with the locale argument so that dates and
   numbers render in the locale's convention. The codebase already
   uses `Intl` in `packages/web/src/utils/format.ts`.
5. **Font selection**: some RTL locales need a different font family
   for proper rendering. Add a `font-rtl` Tailwind class and apply it
   conditionally.

Because RTL support is a substantial undertaking, it is recommended to
add it only when there is confirmed demand for at least one RTL locale.
Adding the locale file alone is not sufficient — the layout will look
broken until the CSS work is done.

## 8. Translation Tooling Recommendations

### 8.1 For Developers

- **i18next-parser** — scans the source code for `t('...')` calls and
  extracts the keys into a template JSON file. Run
  `pnpm --filter @carsai/web i18n:extract` to generate
  `packages/web/i18n-template.json`, which translators can diff
  against their locale file to find missing keys.
- **i18next-scanner** — alternative to i18next-parser with VS Code
  integration. Not currently configured but can be added if the team
  prefers it.
- **eslint-plugin-i18next** — lints for common i18n mistakes such as
  hardcoded strings in JSX. Add it to the web package's ESLint config
  to enforce that all user-visible strings go through `t()`.

### 8.2 For Translators

- **Pontoon** (https://pontoon.mozilla.org/) — Mozilla's open-source
  translation platform. Self-host it and point it at the JSON files in
  this repo for a web-based translation UI with translation memory,
  suggestions, and reviewer workflow.
- **Weblate** (https://weblate.org/) — similar to Pontoon, with
  better GitHub integration. Weblate can open pull requests
  automatically when a translator completes a string.
- **Crowdin** — commercial SaaS with a free tier for open-source
  projects. The easiest option if you do not want to self-host.

For a small project with four locales, a simple workflow (translate
the JSON in a text editor, open a PR) is often faster than setting up
a translation platform. The platform becomes worth it when you have
more than 10 locales or more than 3 active translators.

## 9. Contribution Workflow for Translators

Translators contribute via pull requests against the `main` branch.
The workflow is:

1. Fork the repository and clone your fork locally.
2. Create a branch named `i18n/<locale>-<topic>` (e.g.
   `i18n/fr-blog-namespace`).
3. Edit the relevant JSON file(s) in `packages/shared/src/i18n/`.
   Use a JSON-aware editor (VS Code, JetBrains) so syntax errors are
   caught before commit.
4. Run `pnpm --filter @carsai/shared build` to verify the JSON parses
   correctly. Run `pnpm test` to verify the key-parity test passes.
5. Commit with a message like `i18n: add French translations for blog
   namespace` (Conventional Commits style — see `CONTRIBUTING.md`).
6. Push and open a pull request. In the PR description, list the
   namespace(s) you translated and any keys where the English
   source was ambiguous.
7. A maintainer reviews the PR. Reviews focus on (a) correctness of
   the translation, (b) consistency with existing translations in the
   same locale, (c) preservation of `{{var}}` placeholders, and (d)
   key-parity with `pt.json`.
8. Once approved and merged, the translation ships with the next
   release. The release notes credit the translator by name (or
   GitHub username) unless they request anonymity.

If you are not comfortable with git, you can also open an issue with
the translated JSON attached as a file, and a maintainer will commit
it on your behalf. Either way, your contribution is appreciated and
will be acknowledged.
